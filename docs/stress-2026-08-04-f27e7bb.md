## Follow-up 2: CUDA fault injection

`RUNNER_CUDA_INJECT_FAILURE` forces a device failure so the host fallback can
be proven not to change output. Running it exposed a limitation in the hook
itself.

**The hook could only ever fire on the first device forward.** It was an
unconditional `getenv` check in the prefill tile loop, and the graph fast path
that serves steady-state decode returned before reaching it. So every injected
failure landed on the prefill tile — before a single token boundary had been
crossed — while the comment above it claimed to test failing "after recurrent
state changed". For `qwen35` the interesting rollback is precisely the one it
could not reach: `q35_hist`/`q35_state` snapshotted per forward at
`src/cuda.c:3338`, restored from `*_prev` when a forward fails.

`RUNNER_CUDA_INJECT_FAILURE` now takes a count: **N fails the Nth device
forward**, and the check runs on the graph path too. Unset or `0` disables it;
any non-numeric value means 1, so the previously documented spelling is
unchanged. The message names the ordinal, which is what stops the test from
passing vacuously against a hook that always fires first.

On failure the engine releases the backend and continues on the host for the
rest of the run — one event per run by design, not a missed retry:

```
gpu: injected CUDA runtime failure at device forward 5 — falling back to CPU
gpu: forward failed at runtime — releasing the backend, continuing on CPU
```

## Follow-up 3: a defect the fixture could not show — OPEN

`test-shared-weights` passes against `test.gguf` and **fails against any real
checkpoint**. Found while closing a gap noted during the Linux verification
pass ([`linux-verification-2026-08-04.md`](linux-verification-2026-08-04.md)):
that the device-side VRAM leak check runs at near-zero magnitude, because the
fixture is 370 KB.

```
./test-shared-weights.exe test.gguf                                    # passes
./test-shared-weights.exe C:/ProjectGrid/models/Qwen_Qwen3-4B-Q8_0.gguf  # exit 1
```

Eleven failures, of which the load-bearing ones are:

```
FAIL: every instance uses the same CPU/GPU split
FAIL: instances share one layer array
FAIL: step 0 diverged from the solo reference (a: 0/151936 logits, b: 149477/151936)
```

`bad_a`/`bad_b` are mismatch counts, so `a` is exact and `b` is wrong on
149,477 of 151,936 logits.

### Mechanism

Self-reinforcing, and visible directly in the split lines:

```
gpu-split: budget=7.46GB fixed=0.95GB G=36/36 full=1 used=4.83GB   <- a
gpu-split: budget=3.14GB fixed=0.95GB G=20/36 full=0 used=3.11GB   <- b
```

1. `a` loads against the full budget and takes 36/36.
2. `b` loads, sees only the 3.14 GB `a` left, and **re-decides** its split.
3. A differing split is a differing bind record, so `b` gets its own parse,
   its own file mapping and its own device upload — every sharing invariant
   fails.
4. The differing CPU/GPU boundary changes the arithmetic, so `b` answers the
   same request differently.

This is exactly what `tests/test_shared_weights.c:110-113` says must not
happen: *"A second loader adopts the first one's split rather than re-deciding
against a VRAM figure the first one has already reduced. Slots that disagree
here would run different numbers of layers on the GPU and could answer the
same request differently."* The intent is documented; the implementation
satisfies it only when the naive re-decision happens to agree.

Reproduces on `phi3` as well as `qwen3` — `microsoft_Phi-4-mini-instruct-Q8_0`
gives the same shape, `b` wrong on 199,362 of 200,064. Architecture-independent
and magnitude-dependent.

### Why it was never caught

`test.gguf` is 370 KB. Its weights do not move the VRAM budget, so both loads
choose the same split, take the same bind key, share correctly, and every
invariant passes — vacuously. The Makefile passes that fixture by default and
`ASAN_MODEL` does the same, so the gate has only ever run at a magnitude that
cannot fail it. Every instance in the fixture run reports `0.0 GB weights in
VRAM` and free VRAM never leaves 7.46 GB.

### Not a regression

`8b9282f` changed only the sanitizer path and which parameter the `distinct`
instance varies; with `RUNNER_TEST_GPU_OFF` unset its behaviour is identical to
before. The defect is pre-existing and newly exposed.

### Not fixed here

Still not fixed. The blast-radius question this section originally left open is
settled below, and settling it also refuted the fix direction proposed here.
Tracked as a P1 in the suite-wide plan.

## Follow-up 3a: blast radius and mechanism (2026-08-04, later session)

Investigated on an 8 GB M1 Mac against `9c140d3`. The Mac cannot reproduce the
defect (see the last subsection), so everything below is either read from the
source or observed from a real binary's startup behaviour, and each is labelled.

### `--parallel N > 1` reaches it. Swap mode does not.

**Observed**, `./runner -m models/SmolLM2-135M-Instruct-Q8_0.gguf --serve
--parallel 2 -c 512`: the backend admission line prints **twice**, one
`gpu_init` per slot. That matches `src/server.c:1099-1138` — slot 0 adopts the
model `main()` already loaded, and every slot after it calls
`model_load(s->m, model_path, &slot_mp)` while all earlier slots are still
resident. That is the test's `a`/`b` shape exactly, in production, on the
default non-registry server path.

**Observed**, `./runner -m a=<gguf>,b=<gguf> --serve --parallel 2`:

```
note: model swapping uses a single inference slot; ignoring --parallel 2
```

Registry mode forces `parallel = 1` (`src/server.c:1031-1035`), and `swap_to`
calls `unload_resident()` before the replacement load (`src/registry.c:126-133`),
so two instances of one model are never resident together. Swap is clear.

So the defect is **live, not latent**: it needs only `--parallel 2` and a
checkpoint large enough to trip it. Per-slot drafts are the same shape —
`spec_draft_load(draft_path, ...)` sits inside that same loop
(`src/server.c:1146-1151`), so `--parallel N --draft` loads the draft N times
under the same conditions.

### The proposed fix was already implemented — this is a key MISS

"A loader whose bind key matches an existing record adopts that record's split
rather than re-deciding" is **what the code already does**. `src/cuda.c:1424`:

```c
g->sw = shared_acquire(m, act_bytes, max_hd);
if (!g->sw) goto fail_quiet;
m->gpu_layers = g->sw->gpu_layers;
```

The split is read straight off the shared record, and `shared_matches`
(`src/cuda.c:634-658`) does not include the split in its key. A loader that
matches already adopts, unconditionally.

So `b` did not re-decide *despite* matching. It re-decided *because it did not
match*. Changing the adoption rule would change nothing; the question is why the
lookup missed.

### The host-side miss requires `stat()` to have failed

Both lookups missed in the reported run:

- host — `FAIL: instances share one layer array` means `mw_find`
  (`src/model.c:579-590`) missed;
- device — two `gpu-split` lines with different budgets means `shared_build` ran
  twice, so `shared_matches` missed.

Take the host one, because it is nearly deductive. `mw_find`'s key is the path
string, four stat fields, `kv_q8` and `gpu_mode`. `a` and `b` are handed the
identical path pointer and the identical `model_params`, and they stat the same
unmodified file microseconds apart, so **no field in that key can differ
between them**. A miss therefore requires `id_ok == false` — that is, `stat()`
returned non-zero — or the ~2 KB record `calloc` failing. Both `mw_find` and
`shared_acquire` treat a missing file identity as "load privately, never share"
(`src/model.c:668-670`, `src/cuda.c:1302-1304`), and a private load re-decides
its split against the budget the first instance already reduced. One cause
produces all three reported failures.

The device key is a superset of the same file identity, which is the only input
the two keys share — consistent with the same cause, though the device key has
enough additional fields that it is not deductive on its own.

### Hypothesis for the `stat()` failure: file size

Unverified, and not verifiable on this machine. `mw_file_id`
(`src/model.c:567-576`) and `file_id` (`src/cuda.c:618-627`) both call plain
`stat()` with no Windows path. The same repo already knows that is not enough:
`model_record_file_id` (`src/model.c:64-99`) uses `GetFileInformationByHandle`
on Windows, with a comment saying MinGW's `struct stat` is inadequate, and it
hardcodes `file_ino = 0` there. The Makefile defines no `_FILE_OFFSET_BITS=64`,
and MinGW's default `struct stat` carries a 32-bit `off_t`.

Both reproducing checkpoints are over 4 GB — `Qwen_Qwen3-4B-Q8_0` 4.28 GB,
`microsoft_Phi-4-mini-instruct-Q8_0` 4.08 GB. `test.gguf` is 370 KB. **Nothing
between 370 KB and 4 GB has ever been run through this gate**, so "large enough
to move the VRAM budget" and "large enough to break 32-bit `stat`" have never
been separated. They predict different fixes in different files.

### The experiment that settles it

On the Windows/CUDA box, no code change, minutes:

1. `./test-shared-weights.exe <model>` at roughly 1 GB, just over 2 GB, and over
   4 GB.
   - Red at every size → the trigger is the VRAM budget reduction as originally
     recorded, and the fix belongs in the split path.
   - Green under the 2 GB (or 4 GB) boundary and red above it → the trigger is a
     lost file identity, and the fix belongs in `mw_file_id`/`file_id`, not in
     the split path at all.
2. While it runs, watch stderr for `gpu: reusing resident weights (... now
   shared by N instances)` (`src/cuda.c:1296-1298`). Present for the second
   instance means the device key hit; absent means it missed. That one line
   distinguishes the two mechanisms directly.

Worth doing either way: report `errno` when `stat()` fails at both sites. Today
a failed stat silently downgrades to a private load, which is how a correctness
defect came to hide behind an optimization's fallback path.

### Mac does not reproduce it — recorded so a green run is not read as a fix

8 GB M1, built from `9c140d3`, both **observed**, exit 0:

```
./test-shared-weights test.gguf                               # ok

```

145 MB is 390x the fixture and still passes. That is not evidence the defect is
absent. Metal takes weights zero-copy from unified memory, so a resident first
instance does not reduce the second's budget, and there is no layer split for

does establish is that magnitude alone does not trip the gate on a platform
whose file identity works, which is consistent with the key-miss reading and
does not confirm it.
