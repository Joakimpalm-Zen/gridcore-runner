# Model-shelf stress pass — RTX 3070 box, 2026-08-04 (`f27e7bb`)

Every GGUF resident on this machine (19 files, ~169 GB) re-run against a
`runner.exe` **rebuilt from the sources at `f27e7bb`** ("Fix Windows runner
toolbox tests"), by `scripts/stress-models.py`. Per-model JSON is committed
under `tests/compatibility/out/stress-f27e7bb/`.

This is a **correctness re-validation, not a performance pass.** It was run with
`--no-sweep`, which skips the settings sweep entirely: no `--kv q8` axis, no
`--cpu-moe` axis, no `--bench-json` throughput. The tok/s tables, the
`--kv q8` findings and the per-model launch-line recommendations in
[`stress-2026-08-02-shelf.md`](stress-2026-08-02-shelf.md) are **not** re-measured
here and remain the current measurements. Nothing in this document supersedes
them.

What it does establish is that the two commits landed since that pass — `288daba`
(Apertus CUDA support) and `f27e7bb` (Windows toolbox tests) — did not regress
any model on the shelf.

Machine: Intel i7-7700K (4c/8t), 15.9 GiB RAM (17.11 GB), RTX 3070 8 GiB
(7.46 GiB free at run time), Windows 11. Runner reports `0.1.5-alpha`.
Context 1024, greedy (`--temp 0`), 16 tokens on GPU / 8 on CPU.

Every model that ran was prefix-identical between `--gpu auto` and `--gpu off`

rather than loading it under llama-style math and producing plausible wrong
output. `--caps` currently declares: `llama qwen2 qwen3 qwen35 qwen3moe mistral
smollm stablelm gemma3 gemma4 phi3 gpt-oss apertus`.

## Gemma raw completions — model behavior, not an engine fault

Three Gemma reports contain degenerate raw text and were checked before being
dismissed. From the `-p "The capital of France is"` completion runs:

| Model | GPU text | CPU text |
|---|---|---|
| `gemma-4-12B-it-Q4_K_M` | `...is a beach and a beach is a beach.` | `...is a beach and a beach is a beach` |
| `gemma-4-12B-it-qat-UD-Q4_K_XL` | `...is0111111111111111` | `...is01111111` |
| `gemma-4-26B-A4B-it-Q4_0` | `...is Paris.` then `<|channel>1 2` | `...is Paris.` then `<|channel>` |

**CPU and CUDA agree exactly on the degenerate output**, which already rules the
engine out — a backend bug would make the two disagree, not make them produce
the same nonsense. The cause is the harness prompting an instruction-tuned model
with a bare completion string.

Re-checked today through the chat template, which is the only valid way to judge
these models. All five Gemma checkpoints answer correctly:

```
echo 'What is the capital of France?' | ./runner.exe -m <model> -i --temp 0 -n 24 -c 1024
```

| Model | template | answer |
|---|---|---|
| `gemma-4-E4B-it-Q4_K_M` | `gemma4` | `The capital of France is **Paris**.` |
| `gemma-4-12B-it-Q4_K_M` | `gemma4` | `The capital of France is **Paris**.` |
| `gemma-4-12B-it-qat-UD-Q4_K_XL` | `gemma4` | `The capital of France is **Paris**.` |
| `gemma-4-26B-A4B-it-Q4_0` | `gemma4` | `The capital of France is **Paris**.` |
| `google_gemma-3-12b-it-Q4_K_M` | `gemma` | `The capital of France is **Paris**. 🇫🇷` |

Transcripts: `tests/compatibility/out/gemma-chat-2026-08-04/`. Both the `gemma4`
and `gemma3` template paths are exercised. All five exited 0.

This is the same trap recorded after the 2026-07-20 false "gemma4 Q4_0 bug":
**a raw completion prompt is not a correctness signal for an instruct model.**
`scripts/stress-models.py` uses one deliberately — it is comparing CPU against
CUDA, where identical output is the whole test and coherence is irrelevant — but
its `text` fields must not be read as quality evidence.

## What this pass does not cover

Stated so the green result is not read wider than it is:

- **No settings sweep.** `--kv q8`, `--cpu-moe`/`--cpu-moe auto` and throughput
  were not exercised (`--no-sweep`). In particular the `--cpu-moe auto` fix
  validated on 2026-08-02 is **not** re-tested here.
- **No Apertus or Ornith checkpoint on this shelf.** Both are declared in
  `--caps`; `apertus` gained CUDA support in `288daba`, one commit before the
  binary under test, and its evidence lives in
  `tests/compatibility/out/apertus-cpu-cuda-2026-08-03.json` and
  `divergence-apertus-2026-08-03.json`, not here. The shelf cannot regression-test
  it.
- **One prompt, one context size.** 1024 tokens, greedy, ≤16 generated. Context
  edges are covered separately by `scripts/stress-context.py` (see the 08-02
  pass); long-context, batching and speculative decode are not touched.
- **Completion path only.** No server mode, no OpenAI/Anthropic/Responses
  endpoints, no tool calls or schema-constrained generation, no swap or
  reservation behavior, no failure injection.
- **`gemma4: E-series` caveat unchanged.** The engine still states at load that
  E-series gemma4 is "verified against llama.cpp at the Q4_K noise floor rather
  than token-identically". This pass compares Runner-CPU against Runner-CUDA, a
  different question, and does not revisit that claim.
