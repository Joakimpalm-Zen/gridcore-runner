# Model-shelf stress pass — RTX 3070 box, 2026-08-04 (`f27e7bb`)

Every GGUF resident on this machine (19 files, ~169 GB) re-run against a
`runner.exe` **rebuilt from the sources at `f27e7bb`** ("Fix Windows runner
toolbox tests"), by `scripts/stress-models.py`. Per-model JSON is committed
under `tests/compatibility/out/stress-f27e7bb/`.

This is a **correctness re-validation, not a performance pass.** It was run with
`--no-sweep`, which skips the settings sweep entirely: no `--kv q8` axis, no
`--cpu-moe` axis, no `--bench-json` throughput. The tok/s tables, the
`--kv q8` findings and the per-model launch-line recommendations in
[`stress-2026-08-02-shelf.md`](stress-2026-08-02-shelf.md) are **not** re-measured
here and remain the current measurements. Nothing in this document supersedes
them.

What it does establish is that the two commits landed since that pass — `288daba`
(Apertus CUDA support) and `f27e7bb` (Windows toolbox tests) — did not regress
any model on the shelf.

Machine: Intel i7-7700K (4c/8t), 15.9 GiB RAM (17.11 GB), RTX 3070 8 GiB
(7.46 GiB free at run time), Windows 11. Runner reports `0.1.5-alpha`.
Context 1024, greedy (`--temp 0`), 16 tokens on GPU / 8 on CPU.

## Gemma raw completions — model behavior, not an engine fault

Three Gemma reports contain degenerate raw text and were checked before being
dismissed. From the `-p "The capital of France is"` completion runs:

| Model | GPU text | CPU text |
|---|---|---|
| `gemma-4-12B-it-Q4_K_M` | `...is a beach and a beach is a beach.` | `...is a beach and a beach is a beach` |
| `gemma-4-12B-it-qat-UD-Q4_K_XL` | `...is0111111111111111` | `...is01111111` |
| `gemma-4-26B-A4B-it-Q4_0` | `...is Paris.` then `<|channel>1 2` | `...is Paris.` then `<|channel>` |

**CPU and CUDA agree exactly on the degenerate output**, which already rules the
engine out — a backend bug would make the two disagree, not make them produce
the same nonsense. The cause is the harness prompting an instruction-tuned model
with a bare completion string.

its `text` fields must not be read as quality evidence.

## What this pass does not cover

Stated so the green result is not read wider than it is:

- **No settings sweep.** `--kv q8`, `--cpu-moe`/`--cpu-moe auto` and throughput
  were not exercised (`--no-sweep`). In particular the `--cpu-moe auto` fix
  validated on 2026-08-02 is **not** re-tested here.
- **No Apertus or Ornith checkpoint on this shelf.** Both are declared in
  `--caps`; `apertus` gained CUDA support in `288daba`, one commit before the
  binary under test, and its evidence lives in
  `tests/compatibility/out/apertus-cpu-cuda-2026-08-03.json` and
  `divergence-apertus-2026-08-03.json`, not here. The shelf cannot regression-test
  it.
- **One prompt, one context size.** 1024 tokens, greedy, ≤16 generated. Context
  edges are covered separately by `scripts/stress-context.py` (see the 08-02
  pass); long-context, batching and speculative decode are not touched.
- **Completion path only.** No server mode, no OpenAI/Anthropic/Responses
  endpoints, no tool calls or schema-constrained generation, no swap or
  reservation behavior. (Context edges and failure injection were covered in
  the follow-up below.)
- **`gemma4: E-series` caveat unchanged.** The engine still states at load that
  E-series gemma4 is "verified against llama.cpp at the Q4_K noise floor rather
  than token-identically". This pass compares Runner-CPU against Runner-CUDA, a
  different question, and does not revisit that claim.

## Follow-up 1: context/KV edges (`scripts/stress-context.py`)

Re-run on the same binary across the 12 shelf models at or under the script's
9 GB default, which widens the 08-02 probe (five fully-offloading models) to
partial-offload splits. Report:
`tests/compatibility/out/stress-context-2026-08-04.json`.

- `-c 0` (auto-fit) resolves to 4096 on all 11 supported models and states the
  KV cost. No model failed to run.
- `-c 1000000` is refused on all 11 with the number that made it impossible —
  `cannot allocate buffers (ctx 1000000 needs 131072.0 MB KV cache)` — and
  exits non-zero. No model accepted it.
- `-c 32768` is accepted everywhere, with KV caches up to 12.9 GB
  (`google_gemma-3-12b`) on a 15.9 GiB box.

### The 08-02 usability gap is closed

[`stress-2026-08-02-shelf.md`](stress-2026-08-02-shelf.md) recorded "one real
usability gap": that `-c 32768` is accepted silently and costs ~8× decode,
because the engine "prints the KV size but never connects it to the slowdown."
On this build it connects them explicitly:

```
note: the KV cache for ctx 32768 is 3.62 GB on the device and 33 of 48 layers
ran out of room because of it — a smaller -c or --kv q8 (about half) moves
layers back
```

Named cause, layer count lost, and two remedies. The message landed in
`2633d0b` ("Name the KV-evicts-weights trade") on 2026-08-03, one day after
that document was written, which is why the gap reads as open there. The
acceptance itself is unchanged and still deliberate — a large context is
allowed, it is just no longer unexplained.

### Two defects in the probe, not the engine

Both make the report misleading and are worth fixing before the next run:

1. **`ibm-granite` produces two spurious findings** — "refused a too-large
   context without saying why" and "`--ctx 0` (auto-fit) did not run". Granite
   is refused at the architecture gate, before context handling exists, and its
   message correctly talks about architecture rather than context. The probe's
   keyword heuristic reads that absence as an unexplained refusal. A model
   refused for its architecture should be classified, not scored.
2. **Only the last stderr line is captured** (`last_stderr`), which is the
   throughput line. That is exactly why the KV-pressure note above does not
   appear anywhere in the JSON — the probe cannot see the message that answers
   the question it exists to ask.

## Follow-up 2: CUDA fault injection

`RUNNER_CUDA_INJECT_FAILURE` forces a device failure so the host fallback can
be proven not to change output. Running it exposed a limitation in the hook
itself.

**The hook could only ever fire on the first device forward.** It was an
unconditional `getenv` check in the prefill tile loop, and the graph fast path
that serves steady-state decode returned before reaching it. So every injected
failure landed on the prefill tile — before a single token boundary had been
crossed — while the comment above it claimed to test failing "after recurrent
state changed". For `qwen35` the interesting rollback is precisely the one it
could not reach: `q35_hist`/`q35_state` snapshotted per forward at
`src/cuda.c:3338`, restored from `*_prev` when a forward fails.

`RUNNER_CUDA_INJECT_FAILURE` now takes a count: **N fails the Nth device
forward**, and the check runs on the graph path too. Unset or `0` disables it;
any non-numeric value means 1, so the previously documented spelling is
unchanged. The message names the ordinal, which is what stops the test from
passing vacuously against a hook that always fires first.

On failure the engine releases the backend and continues on the host for the
rest of the run — one event per run by design, not a missed retry:

```
gpu: injected CUDA runtime failure at device forward 5 — falling back to CPU
gpu: forward failed at runtime — releasing the backend, continuing on CPU
```

### Result: output survives a device failure at any depth

Greedy, 16 tokens, `-c 1024`, compared byte-for-byte against the same prompt
run with `--gpu off`. Transcripts:
`tests/compatibility/out/fault-inject-2026-08-04/`.

| Model | arch | split | N=1 | N=2 | N=5 | N=12 |
|---|---|---|---|---|---|---|
| `Qwen_Qwen3.5-9B-Q8_0` | qwen35 (recurrent) | 24/32 | = | = | = | = |
| `Meta-Llama-3.1-8B-Instruct-Q4_K_M` | llama | 32/32 full | = | = | = | — |
| `gemma-4-26B-A4B-it-Q4_0` | gemma4 MoE | 13/30 | = | = | = | — |
| `gpt-oss-20b-MXFP4` | gpt-oss MoE | 13/24 | — | = | = | — |

`=` means the generated text is identical to the pure-CPU run. N=1 is prefill,
N=2 the first decode step, N=5 and N=12 mid-generation with state accumulated.
The recurrent model holds at every depth, which is the result that was not
previously obtainable.

Two permanent gates were added rather than leaving this as a one-off:

- `tests/test_ornith_cpu.py::test_qwen35_cuda_failure_after_recurrent_state_accumulates`
  — injects at forward 2 on the synthetic hybrid fixture and asserts both the
  ordinal and CPU-identical output.
- `tests/test_apertus.py::test_cuda_failure_falls_back_without_corrupting_output`
  — Apertus had CUDA-vs-CPU coverage but no fallback gate; xIELU is the one
  activation with no gate tensor, so a half-applied device result would reach
  the host path without tripping a shape check.

Both run on generated fixtures, so they work in CI with no checkpoint on disk.
