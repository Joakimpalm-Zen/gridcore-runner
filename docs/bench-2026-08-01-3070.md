# Cross-engine benchmarks — RTX 3070 box, 2026-08-01

Reproducible runs from `scripts/compare_llamacpp.py`. Every number here was
produced by that script and its JSON reports are committed beside this file
under `tests/compatibility/out/bench-*/`.

Every engine was given the **identical GGUF file**, not its own conversion of

llama.cpp read the file in place.

## How the numbers are measured, and why it is not each engine's own report

Engines disagree about what they self-report: Runner and llama.cpp return a
`timings` block, Ollama's OpenAI-compatible layer returns none. A table built
from each engine's own accounting is several different measurements printed in
one column. So `compare_llamacpp.py` also derives throughput from the streaming
response alone — arrival of the first token and of the last — identically for
every engine. Where both exist they agree (Runner 105.4 derived vs 106.4
self-reported; llama.cpp 2668.7 vs 2657.4), which is the check that the
derivation is sound.

Two corrections were needed to make these numbers mean anything, both worth
stating because the uncorrected versions looked plausible:

- **Prefill was measuring the prefix cache.** The timing request originally ran
  second, after an identical request had already been served, so both engines
  reported ~16,000–18,000 tok/s "prefill" — a cache hit wearing a throughput
  number. The timing request now runs first and sends `cache_prompt: false`.
- **The correctness gate failed on a renderer artifact.** Top-logprob entries
  are keyed by rendered string because llama.cpp's completions endpoint exposes
  no token ids; the empty string is not a token identity but whatever each
  engine emits for an unprintable token, and the two disagree about which token
  that is. On Ministral-8B that manufactured a 4.59-nat "divergence" while every
  real token agreed to 0.0013 nats. Empty-string entries are now excluded and
  **counted** (129 on that run) rather than silently dropped.

VRAM is exclusive on a single 8 GB card, so engines were measured one at a time,
with only the engine under test holding the GPU (`--endpoints-only` exists for
exactly this). A co-resident run would have reported a spilled engine's host
speed as if it were its device speed.

## gpt-oss — gpt-oss-20b MXFP4 (12.1 GB, partial offload on an 8 GB card)

This is the model the CUDA work in `e1a9676` enabled; before it, the backend
refused the architecture at load and there was no GPU row to report at all.

| Engine | Cold prefill tok/s | Decode tok/s | TTFT s | Placement |
|---|---:|---:|---:|---|
| llama.cpp b10076 | **354.3** | **26.48** | 1.78 | attention on GPU, expert tensors overridden to host (its own choice) |
| **Runner e1a9676** | 4.2 | 0.37 | 153.59 | 13 of 24 whole layers on GPU (`--gpu auto`) |

Greedy text: Runner is **identical to llama.cpp** over all 32 generated tokens
on a 625-token prompt, and the correctness gate passes (max common-token
logprob delta 1.14 nats, below this model's own 0.272→ measured floor class and
well inside the 2.0 gate). That is the result that matters most here: the new
MXFP4 and sink kernels are right.

The speed row is bad, and the reason is placement rather than kernels:

- llama.cpp put **all** attention on the GPU and pushed only the expert tensors
  to the host. Runner's `--gpu auto` instead split at whole layers, so 11 of 24
  layers ran entirely on the CPU — the "worst of both" configuration its own
  split banner warns about.
- Runner has the matching feature (`--cpu-moe`), and with it all 24 attention
  layers do go to the GPU. But `--cpu-moe auto` **over-commits VRAM and the
  forward fails** (14/24 banks placed, 0.69 GB free, `kernel launch failed`,
  fallback to CPU). Capping it manually (`--cpu-moe 20`, 4 banks on device)
  runs correctly but is *slower* than the plain split, because 20 layers of
  expert FFN then execute on the host.
- So on this box every reachable configuration leaves a large share of the
  expert FFN on the CPU, and that is where the time goes. This measurement is
  direct evidence for the backlog item that already names the cause — fused
  quantized VNNI CPU dots — as the dominant lever for MoE models that do not
  fit in VRAM, ahead of any further GPU kernel work.

Both defects were filed with repros; the `--cpu-moe auto` over-commit was
root-caused (an `output.weight` ownership disagreement in the placement
budget) and fixed the next day — the 2026-08-02 shelf pass verified
`--cpu-moe auto` clean on all three resident MoE models, moving gpt-oss-20b
decode 0.37 → 0.38 tok/s and gemma-4-26B 5.9 → 10.8 tok/s on this card. The
numbers in the table above are the pre-fix state.

A third run (`bench-gpt-oss-cpumoe/`, `--cpu-moe 20`) is committed but its
**throughput numbers are not usable and are not quoted here**: llama.cpp's own
figures moved by 6× between it and the run above (58.9 vs 354.3 prefill) on
identical settings, which means the box was thrashing two 12 GB models through
a 15.9 GB page cache, not that either engine changed. It is kept for one
finding only. Its greedy text diverges from llama.cpp at position 22 — and the
divergence is a **near-tie of 0.004 nats** (` rewrite` at −1.47295 against
` write` at −1.47699), with zero GPU fallbacks logged in that run. That is a
coin flip, not an arithmetic fault, and it is precisely why exact-text
comparison is not used alone as a gate here.

## What this says

**Decode is competitive; prefill is not.** Runner decodes at 84% of llama.cpp
on the same file and the same card, which is in line with the decode parity the
performance work has been targeting. Prefill is ~25× behind, and that lands
directly on time-to-first-token: 5.9 s against 0.23 s for a 625-token prompt.

The cause is architectural, not a missing kernel for one quant type. Runner
tiles prefill at `MVB = 16` columns; llama.cpp batches 512-column microbatches
into a real GEMM. Measured on this box with `--bench-json` over a 512-token
prompt:

| Model | Prefill tok/s | Has a tensor-core GEMM twin? |
|---|---:|---|
| Ministral-8B Q5_K_M | 107.8 | no (TC twins exist for Q4_K, Q8_0, Q4_0 only) |
| Llama-3.1-8B Q4_K_M | 173.2 | yes, and promoted for `llama` |

The tensor-core path buys ~60%, and the order-of-magnitude gap survives it. So
the lever is the wide-tile GEMM family already on the backlog ("next-generation
batched MoE GEMM family — wide/multi-column tiles + double buffering", and the
"2D matvec tile" in Phase 6), not more per-quant TC twins. Adding a Q5_K TC twin
would be worth roughly the Q4_K delta and would not close this.

Ollama and llamafile both sit at llama.cpp's numbers, which is expected — both
are llama.cpp derivatives, and this table should be read as *one* independent
implementation (llama.cpp, plus two repackagings of it) against Runner, rather
than as three independent engines agreeing.

**On MoE models that do not fit in VRAM, placement dominates everything else.**
The gpt-oss row is a 70× decode gap that is not a kernel gap: llama.cpp keeps
all attention on the GPU and runs experts on the host, and Runner cannot
currently reach that configuration reliably (`--cpu-moe auto` fails, and the
capped alternative moves too much to the host). Fixing the auto fit is worth
more on this hardware than any further GPU kernel, and the CPU expert dot is
worth more than both.

here reproduce it exactly, and every family checked reproduces itself across
